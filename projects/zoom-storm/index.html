Personal project · architecture study, not a production system

Zoom Storm

A personal marketplace platform built to study and demonstrate distributed-systems patterns in TypeScript.

View repository

Context & problem

In a typical CRUD backend, reads and writes hit the same database and the same model. This project asks what changes when the write model and the read model are deliberately different — different databases, different shapes, kept in sync asynchronously — and what that costs in complexity, consistency guarantees and operational surface.

Objectives

Practice production-oriented distributed-systems patterns end to end in one codebase: CQRS with two databases, event-driven communication via Kafka, transactional outbox for reliable event publication, centralized authentication via OIDC, and full observability — instead of studying each pattern in isolation.

Architecture

The browser only ever talks to the BFF, never to internal services directly. Domain services own their write model in PostgreSQL and publish domain events through a transactional outbox; dedicated projection workers consume those events from Kafka and materialize the MongoDB read models used by the storefront.

Main components

apps/web

Marketplace storefront built with Next.js (App Router), SSR + React Query.

apps/bff

BFF built with Hono: OIDC authentication via Keycloak, Redis-backed session, injects the Bearer token into gateway calls.

apps/api-gateway

Internal routing to cart-service and products-service.

cart-service / products-service

Domain services (cart and marketplace catalog) built with Hono + Clean Architecture; write to Postgres via Prisma and publish events to Kafka.

*-projection (workers)

cart-projection, products-projection, and cart-products-projection consume Kafka events and materialize the read models in MongoDB.

OutboxRelay

The OutboxEvent table is written in the same transaction as the aggregate write; a worker publishes to Kafka and marks publishedAt, guaranteeing at-least-once delivery instead of dual-write.

Technical decisions

  • Clean Architecture per service: domain, application and infrastructure layers separated in each service, with dependency inversion through interfaces/repositories.
  • CQRS with separate databases: writes to PostgreSQL (Prisma), reads from MongoDB, synchronized via Kafka events and projection workers.
  • Transactional outbox instead of direct dual-write: the event is written in the same transaction as the aggregate, then relayed to Kafka.
  • Cart-service replicates the product catalog via cart-products-projection instead of calling products-service synchronously, avoiding coupling and latency between domains at read time.
  • BFF pattern: the browser never talks directly to the gateway; the BFF stores the token in Redis and injects the Authorization header server-side.

Trade-offs

  • Running two databases (PostgreSQL for writes, MongoDB for reads) instead of one adds real operational surface in exchange for read models shaped for the storefront instead of the write schema.
  • The catalog replica inside cart-service introduces a window between a catalog change and its propagation to the cart — accepted in exchange for not calling products-service synchronously on every cart read.
  • At-least-once delivery from the outbox means consumers can see the same event more than once; projections rely mostly on upsert semantics rather than explicit event/aggregate versioning, which is simpler but doesn’t fully protect against an old event overwriting newer state.

Resilience & failure handling

  • Read/write consistency window: PostgreSQL (write) and MongoDB (read) evolve asynchronously via Kafka; projection workers need to be idempotent since Kafka delivers at-least-once and can redeliver the same event.
  • Projection worker recovery: if a projection worker goes down, consumption resumes from the last committed Kafka offset; the outbox relay exists precisely to prevent a failure between the PostgreSQL write and the Kafka publish from leaving the system inconsistent.
  • Per-aggregate ordering: cart-events and checkout-events for the same cart need to be processed in order by cart-projection, which requires partitioning by aggregate key to preserve per-cart ordering as topics scale.
  • Coordinated session across BFF, Redis and Keycloak: expired-token renewal and session invalidation require coordination between the two, to avoid a session that is still valid in Redis but already expired in Keycloak.

Honestly, not everything is implemented: there is no dead-letter queue and no circuit breaker today. A persistently invalid message can keep failing without a quarantine mechanism, and internal calls between the gateway, BFF and services don’t have a consistent timeout/circuit-breaker policy. Kafka events also don’t carry a partition key yet, so ordering guarantees would need that before scaling topics to multiple partitions.

Results & learnings

This is a personal architecture study, not a production system with real users — the useful “results” here are learning outcomes: hands-on experience operating CQRS and outbox at the code level, understanding concretely where eventual consistency actually bites (catalog replication lag), and building observability end to end (OpenTelemetry → Tempo/Prometheus/Loki, visualized in Grafana) instead of only reading about it. It also made the gaps explicit: no CI, no DLQ, no circuit breaker — a clear, honest list of what would come next before this could be operated for real.
