NFEXP

A fiscal-document automation platform for Brazilian micro-entrepreneurs (MEIs), built with a small team.

The repository is private and co-authored with two collaborators, so it isn’t linked here — this page describes the work directly.

Context & problem

Brazilian micro-entrepreneurs (MEIs) who need to issue NF-e fiscal documents typically depend on manual government portals or paid third-party services for every invoice, certificate renewal, and status check. NFEXP automates that flow around a single backend instead of a spreadsheet and a manual portal.

Objectives

Build a backend that owns the full NF-e lifecycle — digital-certificate handling, XML generation and signing, SEFAZ communication, status queries, cancellations, corrections and DANFE (PDF) generation — plus the back-office tooling (stock, clients, billing) around it.

Architecture

A NestJS modular monolith, not a microservices system: one deployable API organized into feature modules (NF-e, stock, back-office, auth, payment), backed by PostgreSQL for transactional data and MongoDB for operational logs, talking to SEFAZ’s SOAP/XML web services for document authorization.

Main components

nfe

Application/domain/infrastructure split for the NF-e lifecycle, with dedicated sub-modules for certificates (cert), products (prod), series (serie), import and PDF (DANFE) generation.

crypto

Digital-certificate parsing and signing (built on node-forge), kept apart from business modules.

stock

Products, entries, exits, suppliers and storage — inventory tracking tied to invoiced items.

backoffice / cliente / dashboard

Client management and operational reporting for the business owner using the platform.

auth

JWT-based authentication guarding the API.

payment

Records a signature/subscription payment entry tied to the user; there is no live payment-gateway integration in the code as it stands today.

Technical decisions

  • Modular monolith over microservices: one deployable NestJS app organized into feature modules, matched to the team size and operational budget of the project rather than a distributed-systems approach.
  • NF-e emission delegated to a dedicated library (node-nfe-nfce) wrapping SEFAZ’s SOAP/XML contracts, instead of hand-rolling XML signing and web-service calls.
  • Certificate handling isolated in its own module, so certificate parsing/signing logic doesn’t leak into business modules.
  • Split storage by access pattern: PostgreSQL (Prisma) for transactional business data, MongoDB (Mongoose) for logs — different write/read patterns use different stores instead of forcing everything into one schema.
  • Server-side PDF/DANFE generation happens after SEFAZ authorization, so the stored document reflects what was actually authorized.

Trade-offs

  • A modular monolith means NF-e, stock and back-office scale and deploy together; simpler to operate at this size, but there’s no independent scaling if NF-e emission under SEFAZ load becomes the bottleneck.
  • Relying on a third-party NF-e library trades control over the SOAP/XML layer for faster delivery — bugs or SEFAZ schema changes are bounded by that dependency’s release cycle.
  • Running MongoDB only for logs alongside a primary PostgreSQL database adds a second datastore to operate for a relatively narrow use case.
  • The payment module currently only records a fixed-cost signature entry — there is no live payment-gateway integration in the code today, so anything beyond record-keeping is out of scope as it stands.

Resilience & failure handling

Fault-handling here is mostly what SEFAZ’s own contract and the node-nfe-nfce library provide, rather than a custom retry/backoff/circuit-breaker layer on top: synchronous request/response against the SOAP service, status queries for polling authorization results, and correction (CC-e) events for fixing details after issuance. Digital-certificate expiry and SEFAZ’s contingency ("ambiente") modes are the realistic failure sources for this kind of integration, and are handled through certificate and environment configuration rather than automated resilience patterns.

Results & learnings

Built with a small team — most of the commit history is mine, with two collaborators — as a working system for MEI fiscal automation, not a project proven at large commercial scale. It's a real integration with a constraint most side projects never touch: digital-certificate signing and a government web-service contract with real consequences for getting it wrong. The main learning was how much of "integration work" in this domain is actually about handling the certificate and SEFAZ’s contingency/environment configuration correctly, not just calling an API — plus the full NF-e document lifecycle (emission, cancellation, correction via CC-e).
